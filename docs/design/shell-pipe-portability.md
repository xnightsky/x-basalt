## 0. 状态：设计提案，未实现

## 1. 为什么要做

接上 shell 管道，x-basalt 才能和**外部工具**组合——上游可以是任何吐路径/JSON 的东西，下游可以是任何吃 JSON 的东西。内置管道解决"我们自己的能力互相串"，shell 管道解决"和别人的东西串"。两件事，后者依赖前者的接缝。

## 2. Windows 上到底卡在哪（本机实测，非推测）

在 `win32` / PowerShell 7.6.3 / 代码页 65001 的开发机上实测：

### 2.1 Windows PowerShell 5.1 会**永久破坏**非 ASCII 数据

`powershell.exe`（5.1）在**每台 Windows 上都存在**，且是大量脚本、任务计划、CI runner 的默认宿主。实测把中文路径经管道送进 native exe：

```
输入：  笔记/测试.md
收到：  bytes: 3   utf8: "﻿"          ← 先来一个 UTF-8 BOM 独立分片
        bytes: 10  utf8: "??/??.md\r\n"    ← 中文被替换成字面 '?'
```

**这不是显示问题，是数据丢失**：非 ASCII 字符在 5.1 的 `$OutputEncoding`（默认 ASCII）下被替换成 `0x3F`，不可逆。对一个以中文笔记为主的 vault，**PS 5.1 下的路径管道是根本不可用的**——这就是当初"卡在 Windows 上"的真身。

对照：同机 PowerShell 7.6.3 下 `$OutputEncoding` = UTF-8，中文完好。

### 2.2 BOM 会作为独立的第一个分片到达

见上：3 字节 `﻿` 单独一个 chunk。**按分片解析的读取器会直接读到一个空/畸形首条**。必须在拼接完整输入后统一剥 BOM，不能按分片处理。

### 2.3 行尾是 CRLF

PS 7 下同样如此：`"笔记/测试.md\r\n"`。按 `\n` 切行会给每条路径留一个尾随 `\r`，**文件查找静默失败**（路径存在却报找不到）。

### 2.4 `jq` 默认不存在

本机实测 `jq: NOT FOUND`。Windows 无内置包管理默认不带 `jq`，`xargs` 同理。

**把 JSON 解析外包给 `jq`，等于把整条管道绑死在一个 Windows 上默认没有的工具上。** 这是 `change-orchestration.md` §8.3「不内置 JSON 猜测（用 `jq`，单一职责）」这条决策在 Windows 上失效的原因——单一职责换来的是这条路在主力平台上根本走不通。

### 2.5 引号与转义有三套互不兼容的语法

`cmd.exe` / PowerShell / Git Bash 对引号、`$`、反引号、`^` 的处理各不相同。**任何要求用户在命令行里手写 JSON 或复杂表达式的设计，在 Windows 上都会退化成转义地狱。**

## 3. 核心设计决策

### D1：输出默认 **ASCII 转义 JSON**

非 ASCII 一律输出为 `\uXXXX`，使载荷成为 **7-bit 干净**的字节流。

实测验证（同一条 PS 5.1 有损管道）：

```
node → ASCII转义JSON → powershell.exe 5.1 管道 → node
recovered: ["笔记/测试.md"]     ← 完好
```

**同一条把裸中文打成 `??` 的管道，ASCII 转义 JSON 无损穿过。** 这一条决策让 x-basalt 的管道输出在**任何代码页、任何 shell**下都安全，代价只是输出体积略增与可读性略降（`--format json` 人读时可关闭转义）。

### D2：内置输入格式嗅探，不依赖 `jq`

推翻 `change-orchestration.md` §8.3。读完 stdin 后按自描述规则判定：

| 首个非空白字符 | 判定 | 取路径的方式 |
| --- | --- | --- |
| `[` | JSON 数组 | 元素是字符串 → 即路径；是对象 → 取 `path` 字段 |
| `{` | NDJSON（逐行对象） | 每行取 `path` 字段 |
| 其它 | 纯文本行 | 每行 trim 后即路径 |

纯文本行模式跳过空行与 `#` 注释行（沿用 §8.3 原契约）。

**理由**：嗅探规则是三条确定性判据，不是"猜"；换来的是零外部依赖。在 Windows 上，"不依赖 `jq`"比"单一职责"重要得多。

### D3：输入侧统一净化

按顺序：读到 EOF 拼完整 → 剥 UTF-8 BOM（§2.2）→ 按 `\r?\n` 切行（§2.3）→ trim → 丢空行/注释。

**BOM 与 CRLF 的处理是无条件的，不做平台判断**——因为数据可能来自任何平台的上游。

### D4：stdout 只放数据，诊断一律走 stderr

管道下游只应看到载荷。warning/info/进度全部 stderr。（现状 `emit()` 已是 stdout 只吐数据，本条是把它变成硬约束并覆盖新算子。）

### D5：检测到有损环境就**显式报错**，不静默产出脏数据

若输入侧发现 `?` 替换字符的特征（连续 `?` 出现在路径位置）或输出侧探测到 `$OutputEncoding` 非 UTF-8 的宿主，**报可诊断的错误并给出修复指引**（升级到 PowerShell 7，或用 `--from-file`），而不是让用户拿到一批查不到的路径。

宁可失败，不可静默错——这是 §2.1 那种"不可逆数据丢失"的唯一正确处理。

### D6：提供不经 shell 的旁路 `--from-file`

在 PS 5.1 这类无法修复的宿主上，用文件传路径列表（UTF-8，不经管道编码层）作为可靠退路。

## 4. 契约

**输入**

- 开关：`--stdin`（或位置 `-`），与 `--pipe` 正交，不塞进 `--pipe`（沿用 §8.3 的正交性结论）。
- 格式：见 D2 三态嗅探；净化见 D3。
- stdin 是 TTY（无管道输入）时**立即报错，不挂起等待**。
- 路径按索引主键形态解析，复用 `manualSourceFromPaths`。

**输出**

- `--format json`（默认，人读，不转义）｜ `json-ascii`（管道安全，D1）｜ `ndjson`（流式）｜ `yaml`。
- 管道场景（stdout 非 TTY）**自动切 `json-ascii`**，人读场景保持可读——默认值随目的地走，用户不用记。
- 永远 UTF-8 **无 BOM**；行尾 `\n`（不跟随平台）。

**退出码**：沿用现有约定（诊断含 error → 1，仅 warning/info → 0）。

## 5. 与算子模型的接缝

在[统一算子模型](pipeline-op-model.md)下，本文**只增加两个算子**，不碰调度层以外的任何东西：

| 算子 | 角色 | 职责 |
| --- | --- | --- |
| `stdin` | 源（`0 → N`） | 读 stdin → 净化 → 嗅探 → `Row[]` |
| `emit [format]` | 汇（`N → 0`） | `Row[]` → stdout（按 D1/D4） |

这正是算子模型 §3.4 那条接缝要买的东西：**外部管道接入退化成"加两个算子"，而不是改执行引擎。** 反过来说，算子模型不先落地，本文就得自己重造一套源/汇机制——这是两篇文档必须有先后的原因。

## 7. 不做

- 不内置 `jq` 的功能（只做 D2 那三条嗅探判据，不做 JSON 查询/变换——那是 `filter`/`map` 算子的事）。
- 不做双向流式协程（读完 EOF 再处理；vault 规模下够用，且避免背压设计）。
- 不为 PS 5.1 做编码修复魔法（`chcp`/`$OutputEncoding` 属用户环境，我们只检测并指引，见 D5）。
- 不开裸 shell 算子（沿用 `change-orchestration.md` §11 与算子模型 §8）。

## 9. 验收口径

1. §6 矩阵每格有实测记录（含失败格的错误信息文本）。
2. 中文路径经 PS 5.1 管道以 `json-ascii` 往返，逐字节相等。
3. 裸文本模式在 PS 5.1 下遇到 `?` 替换字符时报 D5 错误，退出码非 0，且错误信息包含修复指引。
4. 全流程零外部工具依赖（无 `jq`/`xargs` 的环境下端到端跑通）。
5. `--stdin` 在 TTY 下立即报错，不挂起。

## 10. 未决问题

- D5 的"有损环境探测"判据要多严？连续 `?` 也可能是合法文件名。倾向只在**整条输入无任何非 ASCII 且含 `?` 序列**时告警，需要在实现前定判据，避免假阳性。
- `json-ascii` 是否该成为 `--format json` 在非 TTY 下的隐式行为（D7），还是必须显式指定？倾向隐式（用户不用记），但会造成"同一条命令重定向到文件和直接看输出结果不同"，需要权衡。
- Windows 上是否需要同时支持 `--from-file` 与 `--stdin` 的混用（多源合并），还是互斥。倾向互斥，保持源的单一性。
